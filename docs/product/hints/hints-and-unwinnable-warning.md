## Description

Two user-facing features, both backed by the Lonelybot Rust solver bundled into the app as a native module:

1. **Hint button**: a new setting "Hints" (off by default). When on, a Hint button appears to the left of the Undo button in the bottom dock. Tapping it highlights the next move on a winning path from the current position — the card to move (with its valid targets), or the stock if the right move is to draw.
2. **Unwinnable warning**: tell the player when the current position can no longer be won ("no more useful moves"). Stronger than other apps' heuristics because Lonelybot proves it exactly (we have perfect information: face-down identities are known in `GameState`).

Why Lonelybot: already validated offline for deal harvesting (`scripts/generate-solvable-deals-v2.js`), MIT-licensed, extremely fast, and its "thoughtful Klondike" model (all hidden cards known) matches the app's runtime knowledge exactly.

## Research results (2026-07-12/13)

### Desktop performance baseline (M-series MacBook)

`lonecli solve default <seed> <draw>`: 0.03–0.45 ms per solve across seeds 0–42, draws 1/3/5, including unsolvable proofs ("Impossible"). Prior harvest runs used a 5 s timeout as a safety bound; hardest known positions take minutes but are extremely rare. Mid-game positions are typically easier than fresh deals. Phones ~2–10x slower per core → expect single-digit ms typical; a budget handles outliers.

### Lonelybot core API (checkout `/Users/karim/kDrive/Code/Lonelybot/lonelybot`, upstream rev `ae30d39`, core lib locally unmodified, MIT)

- `#![no_std]` + alloc, single-threaded, `unsafe_code = "forbid"`, no global state. Local mods are lonecli-only.
- Card: `Card::new(rank 0..12, suit 0..3)`; internal suit order 0=♥ 1=♦ 2=♣ 3=♠ (HDCS). App order is clubs=0, diamonds=1, hearts=2, spades=3 (CDHS) → remap `[2,1,0,3]` (self-inverse), same as `harvest-v2`'s `app_card_index`.
- Solve: `solver::solve_with_tracking(&mut Solitaire, &impl SearchStatistics, &impl TerminateSignal) -> (SearchResult, Option<HistoryVec>)`; `SearchResult` = `Solved | Unsolvable | Terminated`. Search restores state after run. `TerminateSignal` trait → implement with `AtomicBool` + deadline (lonecli's local `TermSignal` does exactly this).
- Winning path: `HistoryVec = ArrayVec<Move, 1024>` of primitive moves: `DeckStack(Card) | PileStack(Card) | DeckPile(Card) | StackPile(Card) | Reveal(Card)`.
- Human-readable conversion: `convert::convert_moves(&mut StandardSolitaire, &[Move]) -> Result<ArrayVec<StandardMove, 1024>, InvalidMove>`; `StandardMove { from: Pos, to: Pos, card: Card }`, `Pos = Deck | Stack(u8) | Pile(u8)`; `DRAW_NEXT` sentinel = draw one step. A single primitive move can expand to several standard moves (n× draw + play).
- Draw step: `NonZeroU8`, 1–5 fine. Unlimited recycles (deck pointer wraps), matches app rules.
- Hidden cards: `Hidden` stores real identities per column; solver = thoughtful Klondike. Never call `hidden_clear`/`hidden_shuffle`.
- **Gap: no public mid-game constructor.** `Solitaire::new`/`StandardSolitaire::new` take a fresh 52-card deal only; all fields private; `Deck::set_offset`, `Hidden::from_piles`, `Stack` builders are `pub(crate)`. → We vendor the core crate and add a small, clearly-marked public `from_midgame` constructor (see steps). `From<&StandardSolitaire> for Solitaire` exists and handles conversion to the solver representation.
- Search is recursive DFS → run on a thread with 4 MiB stack (lonecli does the same; mobile default stacks are ~0.5–1 MiB).
- Transposition table is an unbounded `HashSet<u64>`; typical visits hundreds→tens of thousands. Budget bounds effective memory. `panic` risk low (asserts are `debug_assert!`); wrap FFI in `catch_unwind` anyway.

### Bundling decision (details + sources in `docs/external-package-guides/rust-mobile.md`, refresh 2026-07-12)

- **Local Expo module `modules/soli-solver/` + hand-written C ABI (JSON strings in/out), not uniffi-bindgen-react-native.** UBRN is still "not yet production" and polls Rust futures on the JS thread; overkill for a 1–3 function API.

### Classic no-more-moves heuristic research (2026-07-23)

Commissioned in feedback round 1 (F4): how do existing apps implement the classic "no more useful moves" warning and hint buttons, how faulty are they, and what should Soli's classic (non-solver) warning check. Sources fetched 2026-07-23.

#### How mainstream apps behave

- **MobilityWare Solitaire** ([FAQ](https://mobilityware.helpshift.com/hc/en/10-solitaire/faq/86-what-does-no-useful-moves-mean/), updated ~2025): "No useful moves" = "no further moves for the current display of cards … other than drawing a new card or undoing". Per-position, event-driven, does NOT scan the remaining stock — a "draw or undo now" nudge that can appear with plenty of stock left. Random deals explicitly not guaranteed winnable.
- **Microsoft Solitaire** (Vista solitaire → Solitaire Collection → Solitaire & Casual Games): "No more moves!" prompt fires right after the triggering move, with end/undo options. Its move definition demonstrably excludes foundation→tableau digs and non-revealing rearrangements (see faultiness). Vista-era versions also sometimes stayed silent when stuck ([narkive thread, ~2008](https://microsoft.public.windows.vista.games.narkive.com/p7drlxQt/solitair-no-more-moves)).
- **Google Solitaire**: reportedly no stuck detection at all — only the win animation; player must notice and re-deal (third-party guides 2025/26 only; low confidence).
- **solitaired.com** ([daily page](https://solitaired.com/daily-solitaire), [app guide](https://solitaired.com/guides/app-guide)): "If no more moves are available, you lose the game"; deals carry offline-solver stats ("moves used by AI to win, if it's a solvable deal").
- **Solebon Klondike** ([site](https://www.solebon.com/klondike-solitaire---ios.html)): no documented no-moves warning; sells "Auto Hints keep the game moving", Winning Deals, "How to Win" replay.
- **Aisleriot** ([klondike.scm master](https://gitlab.gnome.org/GNOME/aisleriot/-/blob/master/games/klondike.scm), hint code ~1998–2008): deliberately NO game-over detection for Klondike. Source comment: the hints miss reversible moves ("unplopping" = foundation→tableau digs, shifts that enable digs) — "so we must NOT report game-over when they run out". Clearest implementation statement found.
- **PySolFC** ([hint.py](https://github.com/shlomif/PySolFC/blob/master/pysollib/hint.py) + `game/__init__.py getStuck()`, master 2026): optional "You are Stuck — There are no moves left…" dialog. Stuck = hint engine at a dedicated stuck level (reversible tableau moves filtered, no foundation digs, flips count) AND, if dealing is still possible, a layout snapshot — warn only when the same dead layout recurs after dealing through the talon. That is the "once per unproductive stock pass" compromise in code.
- **KPat (KDE)** ([apps.kde.org](https://apps.kde.org/kpat/)): the exception — a real solver in the statusbar ("winnable / not winnable in its current state / lost / timeout-unknown", [2009 dev thread](https://mail.kde.org/pipermail/kde-games-devel/2009-April/005455.html)). KDE3's heuristic predecessor was so conservative it almost never fired; the KDE4 solver verdict drew "omniscient guide ruins the game" backlash ([blog, 2009](https://talesfromthearmchair.net/productivity-gains-with-kde4.html)) — the same gameplay change Karim reported for our solver bubble. [TrySolitaire.com](https://trysolitaire.com/how-to-win-solitaire) (2026) likewise advertises a live solver winnable-checkmark.

Summary: commercial apps warn event-driven per move; only PySolFC implements per-stock-recycle timing (via snapshot-revisit, and only for the deal part). Move definitions vary but consistently EXCLUDE foundation→tableau digs and mostly exclude non-revealing rearrangements; MobilityWare doesn't even scan the stock.

#### Faultiness verdict

Documented wrong warnings (said stuck, wasn't):

- [lemoda.net, MS "Patience"](https://www.lemoda.net/windows/patience-bugs/index.html): finishable board; app declared "No more moves!" and even refused the winning jack→queen move; workaround was digging the 5♦ back off the foundation — the classic foundation→tableau miss.
- [Microsoft Q&A, Vegas Klondike](https://learn.microsoft.com/en-us/answers/questions/2677520/vegas-style-klondike-solitaire-in-solitaire-collec): "thinks that all moves have been made when there are still moves to make" — a 6-5-4-3 run had to move between two same-rank 7s (non-revealing rearrangement) to unbury a playable 7♠.
- [PySolFC #565](https://github.com/shlomif/PySolFC/issues/565) (2026-04): "'no more moves' messages when the game is clearly not stuck"; maintainer in [#574](https://github.com/shlomif/PySolFC/issues/574) (2026-06): "every time I fix the stuck check on one game, it seems to cause issues for another".
- [MobilityWare App Store review](https://appsupports.co/1556715867/solitaire-by-mobilityware/negative-reviews): winning deal + undo exploration → "the hints just say no useful moves detected".

False negatives too: Vista solitaire silent when stuck while "giving hints that obviously do not help" (narkive); PySolFC #574 (hints cycle pointless moves forever, stuck never fires). Verdict: shipped heuristics are wrong in both directions; the classic misses are exactly foundation→tableau digs, partial-run moves, and non-revealing-but-unblocking rearrangements. And no mainstream app claims "game unwinnable" from heuristics — every warning is framed as "stuck now: draw, undo, or re-deal"; only solver-backed products (KPat, TrySolitaire; offline winnable-deal databases) claim more. So: our solver bubble stays the strong statement; the classic warning must use the weaker "no useful moves" framing.

#### Hint buttons

Universal commercial pattern: heuristic "any productive legal move"; repeated taps cycle the list; no winnability guarantee — hints happily walk you into losing lines. [MobilityWare hint FAQ](https://mobilityware.helpshift.com/hc/en/10-solitaire/faq/1363-how-does-the-hint-button-work/): shows moves "deemed to possibly be productive", explicitly not all moves. Microsoft: Ctrl+H highlights one valid move at a time. Priority orders from open source:

- Aisleriot: ace→foundation → full-run tableau shifts → waste→tableau → other →foundation builds → text fallbacks ("consider an empty slot" → "deal a new card" → "try moving cards down from the foundation" → "no hint available right now").
- PySolFC `DefaultHint` scores: flip 100k > foundation drops ~90–93k (aces/2s first; deliberately lower when the card may still be needed for building) > tableau moves 80k + bonuses (empties a column +9k, uncovers a face-down +1.5k) > empty column 60k > waste plays ~30k > deal 0. Foundation→tableau only at debug level. Comment in code: "we do not cheat!" (never peeks at face-down identities).

No big app advertises live solver hints; closest are replays of pre-solved curated deals ("Show Me How To Win" / Solebon "How to Win") and solitaired's "AI best moves" marketing. When nothing is found: MobilityWare shows the no-useful-moves message, Aisleriot its text fallbacks, Microsoft the no-more-moves prompt. → Our solver hint is genuinely differentiated; a classic any-move hint would reuse the enumeration below, priority-ordered.

#### Recommended "useful move" enumeration for Soli (draw 1–5, unlimited recycles)

Blend of Aisleriot's exclusions + PySolFC's stuck filter, exact for our single ruleset; pure TS on `GameState`, never reads hidden identities:

```text
usefulMoveExists(state):
  if any tableau top or the waste top plays to a foundation            -> true
  if waste top fits a tableau top, or is a K and a column is empty     -> true
  for each column c with face-up run R (FULL run, from first face-up card):
    for each legal target of R:
      if c.hiddenCount > 0                                             -> true  # reveals
      if c.hiddenCount == 0 and R.base != K                            -> true  # frees a column
      # R.base == K with nothing beneath: can only go empty->empty, pure no-op -> skip (Aisleriot)
  for each column, each partial split of its face-up run:              # PySol step020; cheap, cuts false warnings
    if the split lands legally somewhere and the card it exposes plays to a foundation -> true
  # stock scan, draw-N reachability:
  simulate stock taps from (stock, waste) with NO plays, collecting every waste top,
    until a previously-seen (stock, waste) configuration repeats
    # terminates in <= ~2 full passes: the pre-recycle phase is transient; after one
    # recycle (waste flips back as a block, order restored) each pass is identical
  if any collected card plays to a foundation, fits a tableau top,
     or is a K while a column is empty                                 -> true  # hint: "draw"
  # excluded on purpose: foundation->tableau digs, non-revealing rearrangements —
  # matches every classic app; the solver-proven warning covers exactness
  return false
```

Draw-3/5 pitfall handled: reachability is NOT statically "every 3rd card" — playing a card out of the waste shifts the phase, changing which stock cards can surface. Re-running the whole check after every committed move (fresh simulation from the current stock/waste) keeps the phase correct; never cache the reachable set across moves.

#### When to trigger

After every committed move, debounced (reuse the 600 ms useHint debounce), pure TS on the JS thread — worst case a few hundred comparisons plus a ≤ ~50-tap stock simulation, microseconds. PySolFC checks the stock part only once per unproductive pass because its generic 500-game engine can't cheaply enumerate talon reachability per ruleset; with one known ruleset and a pure reducer we don't need that compromise — same "player has truly ground through everything" semantics, but immediate, without making the player physically cycle the deck. Clear the warning on undo/new position (same position-key mechanism as the solver bubble).

### Microsoft-style stuck warning — deep dive (2026-07-23)

Commissioned in feedback round 2 (F11): pin down Microsoft's exact "no more moves" semantics as the template for Soli's classic warning. Refines the Microsoft bullet in the section above. Sources fetched 2026-07-23. Confidence: [high] = primary evidence (screenshots/official text), [med] = triangulated player reports, [low] = inference.

#### Display form & wording [high]

- Windows 10/11 Microsoft Solitaire Collection, Klondike: MODAL dialog — title "**No more moves!**", body "You have run out of moves. Good game!", buttons **[OK]** (primary) + **[Undo last move]**. Read directly off the [lemoda.net screenshots](https://www.lemoda.net/windows/patience-bugs/index.html) (MSC UWP chrome with score/time bar; images downloaded + inspected 2026-07-23). No "keep playing" button — a Vegas-Klondike user on [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2677520/vegas-style-klondike-solitaire-in-solitaire-collec) explicitly asks Microsoft to ADD a Continue button. OK accepts the loss; the only way to keep the deal alive is Undo last move [med — lemoda author continued only via undo + a different move].
- Lineage: Vista/Win7 wording "There are no more possible moves. What do you want to do?" with End Game / Return and try again (= undo) ([PC Review ~2007](https://www.pcreview.co.uk/threads/spider-solitaire-false-detects-no-more-possible-moves-situation.3428110/), [Win7 Spider Q&A 2011](https://learn.microsoft.com/en-us/answers/questions/2494970/how-to-disable-the-window-that-pops-up-in-spider-s)). Same modal end-or-undo pattern for ~15 years.
- No off switch: Win7-era players asked; unchecking "Show tips" does NOT disable it ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2451544/how-to-disable-the-prompt-there-are-no-more-moves)); none documented for MSC either. Microsoft ships it forced-on — and the complaints ("I want to figure it out for myself, it ruins the game") mirror Karim's round-1 objection verbatim [med].

#### What counts as a "move" — verdict on the generous-model hypothesis

- Counted: tableau→foundation, waste→tableau/foundation, revealing tableau→tableau moves, and — crucially — a legal draw/recycle [med-high, see timing].
- NOT counted, proven by documented false positives on winnable boards:
  - foundation→tableau digs — lemoda: dialog fired although digging 5♦ off the foundation made the board finishable (screenshots confirm diamonds foundation 5♦→4♦ after the workaround) [high];
  - non-revealing run rearrangements — Vegas Q&A: moving a 6-5-4-3 run from 7♠ onto an equal-rank 7♣ (unburies 7♠ for the foundation, flips no face-down card) was not seen; dialog fired right after the 7♣ came down [high for the case, med for the class boundary].
- So the user's mental model ("ANY placement counts; warns only when literally nothing can be placed") is half right: on placements Microsoft is LESS generous than that (it filters digs and rearrangements — exactly where its false alarms come from), on the stock it is MORE generous (an available draw counts as a move, see next).

#### When it is evaluated/shown

- Event-driven, immediate: checked after every committed move; the dialog appears right after the triggering move, not at a stock milestone (lemoda: fired one move after the prior screenshot, score 415→420; Vegas: "the last move was to bring down the 7♣"; Vista Spider: popup appeared mid-card-drag) [high]. NOT once-per-stock-pass.
- BUT in every documented Klondike firing the deck was already exhausted (lemoda: stock empty + the last waste card just played; Vegas: "all the cards are played"). No report found of it firing while a draw/recycle was still legal; Vista-era reports show the opposite failure — genuinely stuck, deck non-empty, silence plus useless hints ([narkive ~2008](https://microsoft.public.windows.vista.games.narkive.com/p7drlxQt/solitair-no-more-moves)). Best-evidenced model: **a legal draw/recycle suppresses the warning entirely — Microsoft never claims knowledge of unseen stock; the player must play the deck out (or use up Vegas passes) before it will declare no-more-moves** [med — fits all positive and negative evidence; partly an absence-of-reports argument].
- Draw-3 phase subtleties: undocumented; unknowable without instrumenting the app [low].
- Reset/re-warn: re-fires after EVERY move that re-enters a dead state (lemoda: "keeps on banging on and on" as he re-tried the jack move); any move/undo resets it. Effectively once per dead position, not once per game [high].

#### False-warning move classes (what Soli's solver gate rescues)

1. foundation→tableau dig wins the game (lemoda) [high]; 2. equal-rank run shift unburies a playable card (Vegas Q&A) [high]; 3. partial-run splits ([PySolFC #565](https://github.com/shlomif/PySolFC/issues/565) documents the class genre-wide) [med]. More modern-MSC false positives without board detail: [expert-Klondike daily challenge "tells me I am out of moves and I am not"](https://www.windowsphoneinfo.com/threads/microsoft-solitaire-collection-wont-open-daily-games.725229/), [FreeCell "ended with plenty of moves left"](https://learn.microsoft.com/en-us/answers/questions/2721669/solitaire-collections-games-ending-before-im-finis) [med]. Opposite failure exists too (Vista: stuck but silent) [med]. Soli mapping: heuristic-stuck AND solver-unsolvable → warn; heuristic-stuck but solver-solvable → suppress + log (rescues exactly classes 1–3); heuristic-not-stuck but solver-unsolvable → classic warning stays silent by design (that stronger claim belongs to the separate solver-warning setting).

#### Mainstream equivalents (genre expectation, one line each)

- MobilityWare: non-modal repeating toast "No useful moves" per display state — official FAQ: "no further moves for the current display of cards … other than drawing a new card or undoing"; fires with stock remaining, reappears after every fruitless draw incl. right after a recycle flip; never force-ends the game [high].
- Solitaired: loss framing — "if no more moves are available, you lose the game" [med].
- Zynga Klondike: no stuck warning documented; store copy sells "Use Shuffle when you are stuck" (power-up instead of warning) [med-low].
- Default-ON is the genre norm (Microsoft forced-on, MobilityWare on; no opt-outs documented anywhere) — supports classic warning default ON [med].

#### Recommended Soli spec (classic warning)

- Move definition: the `usefulMoveExists` enumeration above (foundation plays, waste plays, revealing/column-freeing run moves, foundation-enabling splits, plus exact reachable-stock simulation for draw 1–5 with unlimited recycles). Same exclusions as Microsoft (no foundation digs, no pure rearrangements) so the player-facing semantics feel identical — but our stock handling is strictly better: we prove "drawing won't help either" phase-correctly instead of requiring the player to grind the deck out.
- Gate: never display on the heuristic alone — require solver `unsolvable` on the same position key (existing 800 ms background path). Log suppressed cases (`heuristic stuck, solver solvable`) for QA; that log is the live counter of Microsoft-style false positives we prevented.
- Display timing — evidence vs user preference (user remembered "shows when you flip the stock back to the first card"; evidence says no mainstream app does that — Microsoft is event-driven-but-deck-exhausted, MobilityWare immediate/repeating; PySolFC's once-per-pass snapshot is an engine-cost compromise we don't share):
  - Option A (recommended): evaluate and show right after the triggering move (reuse 600 ms debounce), non-modal bubble. Matches the real genre norm, and since it only fires on solver-proven dead positions it cannot change strategy — undo or re-deal are the only continuations; earlier display just saves pointless deck-grinding.
  - Option B (user's remembered timing): identical evaluation, but hold the bubble until the player's next recycle tap (show immediately if stock+waste are already empty — Microsoft's actual firing case). Pro: the player has physically seen the cycle, so the warning reads as confirmation rather than oracle (no "how does it know cards I haven't seen?" moment). Con: lags the dead moment by up to a full pass, never shows if the player stops cycling, and matches no shipping app.
  - Recommendation: A. If playtest shows the mid-stock oracle-feel bothers, add B's display-hold as a refinement — the evaluation code is identical either way.
- Form/wording: non-modal bubble (existing `UnwinnableBubble` styling), no buttons, never blocks input — MobilityWare's form, not Microsoft's modal (the modal + missing Continue is the single most-complained-about part of Microsoft's design). Copy: "No more useful moves — undo or start a new game" (weak/classic framing per the faultiness verdict; reserve "unwinnable" wording for the solver setting).
- Reset semantics: mirror Microsoft — keyed to the existing position-key mechanism; any committed move/undo clears it; re-shows on each new dead position.

## FFI contract (single source of truth — Rust and TS must both follow this)

One exported function (plus a string-free): `soli_solver_solve(request_json) -> response_json` (caller frees via `soli_solver_free_string`).

Request JSON (app suit/rank conventions; card = `"<suit letter c|d|h|s><rank 1..13>"`, e.g. `"c1"` = A♣, `"s13"` = K♠):

```json
{
  "drawCount": 3,
  "budgetMs": 1500,
  "foundations": { "c": 2, "d": 0, "h": 1, "s": 0 },
  "tableau": [ { "hidden": ["d4", "s9"], "visible": ["h10", "s9"] } ],
  "stock": ["h2", "c7"],
  "waste": ["s5", "d12"]
}
```

- `foundations`: number of cards already on each foundation (2 = A,2 placed).
- `tableau`: exactly 7 entries; `hidden` and `visible` both ordered bottom→top (app column order). `visible[0]` sits on `hidden[last]`.
- `stock`: app order — **last element is drawn next** (app pops from end).
- `waste`: app order — **last element is the top/playable card**.
- Suit remap CDHS↔HDCS happens inside Rust (mirroring `harvest-v2`), so TS stays dumb.

Response JSON:

```json
{
  "status": "solved",
  "solveMs": 1.8,
  "visited": 3084,
  "winMovesRemaining": 42,
  "hint": { "kind": "move", "card": "d7", "from": { "type": "tableau", "index": 3 }, "to": { "type": "foundation" } }
}
```

- `status`: `solved | unsolvable | unknown | invalid | error` (`unknown` = budget hit; `invalid` = state failed validation; `error` = internal/panic).
- `hint` only when `solved`. `kind`: `draw` (tap stock once — even if several draws are needed before the play, one hint = one draw) or `move` with `from` ∈ tableau(index)/waste/foundation(suit), `to` ∈ tableau(index)/foundation. Derived from the first primitive move of the winning path via `convert_moves`; if the first standard move is `DRAW_NEXT`, the hint is `draw`.
- `winMovesRemaining`: primitive move count of the found line (for logs/QA).

Feedback round 4 — F16 (2026-10-11):

- **"Stale" was the wrong frame for dead-proofs**: the F14 code dropped every background result whose position key no longer matched (`stale || keyAtRun !== key`). For a hint that is right (a ring for an old board is nonsense), for an unsolvable proof it is wrong — the DeadEraMarker invariant already says forward moves keep a dead game dead, so the proof stays valid for every forward descendant. The fix is to carry the EVALUATED board with the result (snapshot solves) and judge by era membership (`same exactId && history.length >= evaluated depth`), not by key equality. Position keys are still the right tool for the hint path and the unwinnable-mode debounce guard.
- **Snapshot solves make the queue semantics explicit**: `makeSolveTask` used to serialize `stateRef.current` at RUN time ("always solve the newest position"), which silently meant the handler could never know which board a result was about. Passing the board in at enqueue time costs nothing (the replace-latest queue still drops superseded tasks before they start) and is what makes rule 2 possible. For the hint press the snapshot equals the press-time board, so behavior there is unchanged.
- **Immediate evaluation reorders the fire-on-discovery race**: with the end-of-stock solve starting synchronously in the effect, a hint press at the flip can only queue BEHIND the background proof — so the press's own unsolvable result lands second and must not fire/announce again (new era guard in the hint handler; the old F15 test "press before the debounce" became impossible in mode noUsefulMoves and was rewritten around the in-flight race). Fire-on-discovery via the press in that mode is now only reachable when the background proof returned 'unknown' (budget miss) — tested.
- **Reading `stateRef.current` synchronously inside the effect is deliberate**: depending on `state` would re-run the effect (and the heuristic + a solve at stock 0) on every selection tap, which changes the state object but not the position key. The ref is synced by an earlier-declared effect in useKlondikeGame, so it IS the committed board when useHint's effects run (same as the test harness, which assigns it during render).
- **Known residual window (accepted, flagged)**: era membership is checked by depth, so an undo below the evaluated depth followed by a different forward move to depth ≥ boundary, all WITHIN the solve's flight time (typically < 1 ms, max 800 ms budget), would let the proof fire for a line it did not evaluate. Physically implausible for a human (two deliberate taps inside the solve window); an "undo generation" counter would close it exactly if ever needed.
- **`adb shell input tap` bursts drop taps that land during the draw animation** (device): 5 taps ~50 ms apart on the stock registered 4 — the recycle tap was swallowed. ### Solver-side line-quality feasibility (2026-07-23)

F12 deliverable (analysis only, nothing implemented): could the vendored lonelybot search itself produce more human-friendly winning lines (board-first, fewer draw streaks, shorter), instead of / beyond the app-side F9 fix (enumerate no-draw progress moves, verify each with a sub-solve, hint the first that stays winnable)? Facts from `rust/vendor/lonelybot/src/`:

- **Ordering does pick the line, not just the speed**: the solver returns the FIRST line DFS finds (`SolverCallback::on_win` returns `Halt`, solver.rs:33-36) and `traverse` tries moves in exactly the order `MoveMask::iter_moves` yields them (traverse.rs:95).
- **That order is already board-first**: Reveal → PileStack → DeckPile → DeckStack → StackPile (moves.rs:106-120); foundation digs are last; within a type, ascending card index (`Card::from_mask` = trailing_zeros, card.rs:109-117) — no draws-needed awareness.
- **Draws don't exist inside the search**: the 5 primitive move types (moves.rs:10-16) treat the deck as a reachability mask (`Deck::compute_mask`); `convert_moves` expands one deck move into n×DRAW_NEXT+play only afterwards (convert.rs:15-35). "Fewer draws" is not expressible as a search cost without threading deck-offset math through the search.
- **The biggest cause of draw-first lines is ordering-IMMUNE**: dominance forcing returns single-move masks that bypass iteration entirely — forced pile→stack (state.rs:178-184), ≥3-redundant collapse (:190-195), forced deck→stack (:198-206); on draw-1, ANY dominance-safe deck card (e.g. a buried ace) makes that lone deck move the node's only child (`get_deck_mask`, state.rs:136-143). That alone explains the ~18-draw fresh-deal streak in Follow-up #4. These forcings are also why solved positions visit only ~100 states (perf tables) — weakening them for line quality trades orders of magnitude of search perf.
- **Reordering is sound**: pruning is a mask filter computed before iteration (traverse.rs:85-87, `FullPruner::prune_moves`), the TP table is a plain visited-set (traverse.rs:81) — both order-independent. But TP-cut path dependence means a preference order only *tends* to shape which line is found.

### Artifacts-in-git decision (2026-07-23)

**Decision: do NOT commit the built solver artifacts. Commit only Rust source; gitignore all build outputs; add a fingerprint-based ensure step that auto-rebuilds (toolchain present) or fails loudly (toolchain missing) in every build path; add a root `.easignore` so the locally built artifacts still upload to EAS.** Resolves F10 and Follow-up 2. Research done 2026-07-23 (web + repo).

**Research summary** (sources fetched 2026-07-23):

- Canonical git practice: derived binaries don't belong in history; store them in artifact storage or rebuild in CI ([SE: "Do products of a build process belong in a repository?"](https://softwareengineering.stackexchange.com/questions/331774/do-products-of-a-build-process-belong-in-a-repository)). Git packs can't delta binaries — measured here: the 57 MB XCFramework gzips to ~18 MB, so every solver release committed would permanently add ~18 MB to `.git` (which kDrive also syncs — each artifact version stored twice: pack + working copy). The 38 MB sim `.a` is one growth step from GitHub's 50 MB per-file warning. Not catastrophic at "a handful of updates", but permanent and avoidable.
- Rust-in-mobile ecosystem norm: nobody commits XCFrameworks/`.so`s to the repo. Library repos build in CI and attach `*.xcframework.zip` to GitHub Releases, consumed via SPM `binaryTarget` URL+checksum ([Mozilla application-services megazords/ios-rust](https://github.com/mozilla/application-services/tree/main/megazords/ios-rust), [firefox-ios Package.swift](https://github.com/mozilla-mobile/firefox-ios/blob/main/MozillaRustComponents/Package.swift), [Ferrostar](https://stadiamaps.com/blog/ferrostar-building-a-cross-platform-navigation-sdk-in-rust-part-2/)). App repos with vendored Rust build from source on the build machine / EAS workers via `eas-build-pre-install` ([Expo build lifecycle hooks](https://docs.expo.dev/build-reference/npm-hooks); real examples: [vouch-protocol expo-sonic](https://github.com/vouch-protocol/vouch/blob/main/mobile/expo-sonic/README.md), [claas.dev Expo-with-Rust](https://claas.dev/posts/expo-with-rust/)).
- EAS mechanics — the pivotal constraint ([expo/fyi eas-build-archive](https://github.com/expo/fyi/blob/main/eas-build-archive.md), [easignore docs](https://docs.expo.dev/build-reference/easignore)): the upload archive = working-dir files minus `.gitignore` matches, so gitignored artifacts would NOT reach EAS by default and cloud iOS builds would break. But a root `.easignore` REPLACES `.gitignore` for uploads and is the documented way to upload non-committed files. `requireCommit` defaults to false (we don't set it); `eas build:inspect -s archive` verifies the upload. EAS `cache.paths` is a best-effort perf cache only ([caching docs](https://docs.expo.dev/build-reference/caching/)) — never a correctness mechanism.
- git-lfs in 2026: GitHub Free now includes 10 GiB LFS storage + 10 GiB bandwidth/month, $0.07/GiB beyond ([GitHub product-usage docs](https://docs.github.com/en/billing/reference/product-usage-included)) — quota is a non-issue at our scale. Rejected anyway: adds clone/tooling friction and a new silent-failure mode (pointer files where binaries should be, incl. inside EAS archives) for zero benefit once artifacts aren't committed at all.
- Dynamic-library XCFramework to shrink the 57 MB: rejected. The cargo-xcode maintainer is blunt — "use static libraries whenever possible; dynamic libraries are much harder to build, much harder to embed correctly, and add bloat" ([cargo-xcode docs](https://docs.rs/crate/cargo-xcode/latest)); CocoaPods has known mixed static/dynamic vendored-framework failures ([CocoaPods#12172](https://github.com/CocoaPods/CocoaPods/issues/12172)). Once nothing is committed, the fat sim slice costs nothing (never ships; only ~0.5 MB survives app linking).
- Silent-staleness angle (why this beats committing even on the "must always build" axis): a committed artifact goes silently stale when `rust/` changes without a rebuild — git cannot detect that. The fingerprint check detects exactly that and self-heals. Commit-Android-`.so`-only was also rejected: two mechanisms, and rebuilt `.so` bytes differ per toolchain → perpetual dirty diffs.
