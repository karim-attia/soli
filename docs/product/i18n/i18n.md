## Description

**Framing.** Soli is English-only today. All user-facing text is hardcoded in ~25 files (screens, settings descriptors, alerts, a11y labels, HUD, hint bubbles). Solitaire is a universal game with a large non-English audience ("Solitär", "Patience", "Косынка", "接龙", "ソリティア"), and the stores rank and convert per language.

**Leading words.** OS language (no in-app picker) · English JSON is the source of truth · glossary is the authority for terms · translations are produced by translator sub-agents, never typed ad hoc · cheap mechanical gates (jest) catch drift · board stays left-to-right in every language.

**What we do.**

1. i18n infrastructure: `expo-localization` + `i18next`, typed keys, 15 locale JSON files (en source + de [Swiss High German], fr, es, pt-BR, it, nl, ja, ru, pl, tr, zh-Hans, ko, ar, he).
2. Extract every production string (~120 keys) to `en.json`; dev-only UI stays English.
3. RTL (ar, he): app chrome mirrors, the whole game surface is pinned to `direction: 'ltr'`.
4. Glossary (`docs/product/i18n/glossary.md`) built from per-language online terminology research, plus a translator skill (`.agents/skills/soli-translation/SKILL.md`) modelled on Mango Inventory's `code-translator` + glossary + new-language playbook, without its heavy tooling.
5. Store listings in the repo (`store/`): per-locale App Store + Google Play text and the screenshots, translated in the same run. Uploading is NOT part of this run.

**Why it is nice and important.** "Best Solitaire app in the world" is not English-only; translation cost with LLM sub-agents is tiny at ~120 strings; a glossary + parity test keeps quality from rotting; store text in git makes listings reviewable and reusable (also by F-Droid-style tooling later).

## Acceptance Criteria

- German is **Swiss-only**: every German-speaking device (`de-CH`, `de-DE`, `de-AT`, …) gets the one `de` locale, written in Swiss High German (always ss, never ß; Swiss vocabulary where it differs).
- `pt-PT` device → Brazilian Portuguese (better than English); `zh-Hant` device → English (see Open questions).
- The first device language we support wins (device list `[it-CH, de-CH]` → Italian; `[rm-CH, de-CH]` → German), matching what iOS itself picks for the app.
- iOS Settings → Soli → Language and Android 13+ App language list the supported languages; switching there changes the app (iOS restarts the app; Android: correct after returning to the app, without losing the running game).
- Arabic/Hebrew: settings, history, drawer, headers mirror; the game screen (HUD, foundations, stock/waste, tableau, card flights, hint rings, celebration, undo scrubber, dock buttons) looks and behaves exactly as in English, only texts are translated. History board preview is also LTR.

- Card faces stay A/J/Q/K with the generated card fonts. Numbers on the game screen use Latin digits in every locale.
- Dates in History are formatted in the app language with the device region (`de-CH` → "6. Juli, 17:33").
- No truncated/clipped labels on header button, dock buttons, HUD badges, settings rows, history stats row on a small phone (iPhone SE-class width / the Android phone) in de, ru, fr (long languages).
- `yarn typecheck && yarn lint && yarn jest` pass; jest fails when a locale misses a key, has different `{{placeholders}}`, misses a CLDR plural form, or when an English value changed without re-translation.
- Engine (`src/solitaire/`) contains no user-facing English any more and imports nothing from `src/i18n`.
- `store/` holds, per store locale, title/name, subtitle, short description, full description, keywords, promotional text, release notes; a jest test enforces store character limits. Current live screenshots are saved there.
- `docs/product/i18n/glossary.md` has a column (and writing rules with source links) per language; `.agents/skills/soli-translation/SKILL.md` exists; AGENTS.md points to it (after Karim's OK).

## Possible approaches

### A. i18n library

| Option | Pros | Cons |
|---|---|---|
| **A1 `i18next` + `expo-localization`, no `react-i18next` (recommended)** | One runtime dep less; `t()` is a plain import usable in components, hooks, `Alert.alert` callbacks and the pure a11y helpers without changing ~20 function signatures; React Compiler-safe by construction (see C) | Deviates from the accepted "i18next + react-i18next"; no `<Trans>` (not needed: one inline link in `hello.tsx`, solved by copy) |
| A2 `i18next` + `react-i18next` (`useTranslation`) | Idiomatic, most documented | With the React Compiler, a helper called in render (`getStockLabel(count)`) is memoized on its inputs → stale after a runtime language change unless `t` is threaded through every helper signature (a11y helpers, HUD row builder, hint announcement, formatters, their tests). More code, more churn, for a case (language change while running) that only exists on Android |
| A3 `expo-localization` + `i18n-js` | Tiny | Weak typing, plural handling for ar/ru needs extra setup, less maintained |
| A4 Lingui / FormatJS | ICU MessageFormat, extraction | Babel macro/compile step + Intl polyfills on Hermes; overkill for ~120 strings |

Recommendation: **A1**. If the remount in C misbehaves on device, fall back to A2 (documented in Steps as the contingency) — the JSON files, keys and tests are identical for both.

Versions (checked 2026-11-23 with `npm view` and `node_modules/expo/bundledNativeModules.json`): `expo-localization ~58.0.4` (install with `npx expo install expo-localization`), `i18next 27.2.6`, (`react-i18next 18.0.3` only for the A2 contingency; peers `i18next >= 27.0.1`, TypeScript `^5 || ^6 || ^7`).

### B. Language resolution

- **B1 (recommended): own pure resolver** `resolveAppLanguage(getLocales())` in `src/i18n/resolveLanguage.ts`: walk the device's ordered locale list, return the first supported app locale. Rules: match by language code (`de-*` → `de`, no region rule — German is Swiss-only); `pt-*` → `pt-BR`; `zh` with script `Hans` or (no script and region not `TW`/`HK`/`MO`) → `zh-Hans`, other `zh` → skip; legacy Android code `iw` → `he`; nothing matches → `en`. i18next gets that exact key as `lng`, `fallbackLng: 'en'`, `supportedLngs` = the 15 keys, `load: 'currentOnly'`.
  - Why not `getLocales()[0]` + i18next's own matching: `[0]` is the user's FIRST language even when we don't support it (device `[rm-CH, de-CH]` → would give English while iOS runs the app's native parts in German); and i18next's `nonExplicitSupportedLngs`/`load: 'languageOnly'` cannot express `pt-PT → pt-BR` or `zh-TW ≠ zh-Hans`. 25 lines + a table-driven unit test are simpler to reason about than three interacting i18next options.
- B2: `lng = getLocales()[0].languageTag` + `nonExplicitSupportedLngs: true`. Less code, wrong in the cases above.

### C. Reacting to a language change (Android does not restart the app; iOS does)

- **C1 (recommended): language is constant for the lifetime of a mounted tree.** `src/i18n` exports `syncLanguage()`; the root layout re-runs it on `AppState` → `active`; if the resolved language changed it calls `i18n.changeLanguage()` and bumps a `key` on the root wrapper so the whole tree remounts — the same thing iOS does by restarting. No `t()` at module scope anywhere. Pros: one mechanism, compiler-proof (remount drops every memo cache), plain `t()` everywhere. Cons: a remount resets navigation to the Play screen and re-hydrates the game from storage (must be verified: the game is persisted when the app goes to background; Android may recreate the Activity on a locale change anyway since `locale` is not in `android:configChanges` — verify what actually happens).
- C2: `useTranslation()` everywhere (A2). See A2 cons.
- C3: ignore runtime changes on Android (new language after next cold start). Zero code, but a visible bug.

### D. Translation workflow / stale detection

| Option | Pros | Cons |
|---|---|---|
| D1 Mango-style `todo`/`apply` CLI + hash sidecar per locale | Proven, per-key stale tracking | ~1000 lines of tooling for 120 strings |
| **D2 (recommended): translators write the locale JSON directly; one snapshot file** `src/i18n/locales/en.last-translated.json` (= `en.json` as of the last full translation). Jest fails when an `en.json` value differs from the snapshot and names the keys | ~15 lines of test; works because all locales are always re-translated together; the fix is "run the translation skill for these keys, then copy en.json over the snapshot" | No per-locale state (fine: we never translate locales at different times) |
| D3 no stale detection | Nothing to maintain | A reworded English string silently keeps 15 old translations |

Parity test (all options): same key set as `en.json` (plural keys compared by base name), same `{{placeholder}}` set per key, exactly the plural forms from `new Intl.PluralRules(locale).resolvedOptions().pluralCategories` for every plural key, no empty values, no value identical to English unless listed in an `UNTRANSLATED_OK` allow-list (e.g. "Vegas", "Soli").

### E. Store listing layout

| Option | Pros | Cons |
|---|---|---|
| **E1 (recommended): `store/` with fastlane-shaped text files** — `store/android/<play-locale>/{title,short_description,full_description}.txt`, `store/ios/<asc-locale>/{name,subtitle,description,keywords,promotional_text}.txt`, `store/release-notes/<locale>.txt`, `store/screenshots/{ios,ipad,android}/<locale>/`, `store/README.md` | Plain text diffs; one file per field = easy limits test; same shape as fastlane `supply`/`deliver` (`--metadata_path store/android` / `store/ios`), so future tooling needs no migration; a later `store.config.js` for EAS Metadata can read the iOS files | Not literally `fastlane/metadata/android/` (the path F-Droid auto-reads) — a symlink or move is a one-liner if F-Droid ever matters |
| E2 `store.config.json` (EAS Metadata) as the source | Directly uploadable for iOS | Apple only (EAS Metadata does not support Google Play — verified in the schema docs 2026-11-23), no screenshots, one big JSON is awkward for translators and limits |
| E3 literal `fastlane/` folder | F-Droid reads it | A `fastlane/` folder without fastlane confuses; iOS and Android trees are laid out inconsistently |

Screenshots: the current sets contain **no captions or marketing text** (plain app screenshots, see `docs/product/store-screenshots/store-screenshots.md`); the board is language-neutral, only HUD labels/"New Game"/settings/history texts differ. Both stores fall back to the primary language's screenshots. Recommendation: **save the live English set in the repo now, no localized screenshots in this run**; localized Settings/History shots are a follow-up (cheap later with `-AppleLanguages` + the existing screenshot mode).

### F. German: Swiss-only (decided, Prompts 4–5)

One locale `de`, written in **Swiss High German** (always ss, never ß; Swiss vocabulary where it differs), for every German speaker — in the app and in the one German store listing.

| Option | Pros | Cons |
|---|---|---|
| **A Swiss-only (chosen)** | One German to maintain; authentic "made in Switzerland"; no resolver rule, no fallback chain; matches what Swiss-origin apps do | Germans/Austrians may read "Spass"/"gross" as a typo — mitigated by saying "Made in Switzerland" in the listing and by preferring words without ß/ss contrast where a neutral synonym exists |
| B `de-CH` + derived `de` (ß) | Orthographically right for both audiences | Two files and two review passes per change; nobody among the Swiss apps checked does this |
| C standard German (ß) only | Right for the biggest market | Wrong for the maker's home market; not what Karim wants |

Evidence (orchestrator research, 2026-11-23; restate with these links in the glossary's German rules):

- Threema: one German in ss everywhere — https://www.github.com/threema-ch/threema-android
- Infomaniak kDrive: in-app `values-de` has 0 ß — https://github.com/Infomaniak/android-kDrive
- SBB, MeteoSwiss, Migros, Coop, Swiss Post, NZZ, 20 Minuten: ss even in the DE and AT App Store storefronts.
- Global-first Swiss firms (Proton, Smallpdf, GIANTS) use ß. **Nobody splits de-CH/de-DE.**
- Neither store has a de-CH listing locale: App Store localizations https://developer.apple.com/help/app-store-connect/reference/app-information/app-store-localizations ; Google Play https://support.google.com/googleplay/android-developer/table/4419860

Guard against well-meant "fixes": a header comment where `de` is registered in `src/i18n/index.ts`, a bold rule at the top of the glossary's German section, a line in the translation skill, and a jest assertion that `de.json` + the German store files contain no `ß`.

## UX/UI Considerations

- **No in-app language picker.** Language = OS / per-app language setting.
- **Text length.** German/Russian/French run 20–35 % longer. Tight spots to check on device: header "New Game" action button, dock "Hint"/"New Game" buttons (`DockActionButton`), HUD badges (Score/Moves/Time/Vegas/Total), "Draw" caption on the stock card back and "2 left" on the recycle back (11 px, clipped with `ellipsizeMode="clip"`), settings picker values ("No more useful moves"), history stats row (Games/Solved/Incomplete), history sheet buttons, Alert button labels (Android truncates long alert buttons). The glossary's "short labels" rule tells translators to prefer the short word there; the en.json `_comment`-style context (see Components) marks those keys as `tight`.
- **RTL (ar, he).** Chrome mirrors natively (drawer side, header, Expo UI `FieldGroup`/`Picker`/`Switch`, history list rows). The game surface is pinned LTR with `style={{ direction: 'ltr' }}` on the root view of the game screen (board + HUD + dock/scrubber + bubbles + celebration overlay) and on `BoardPreview`; texts inside bubbles keep natural bidi. Reason: card positions, flight animations, hint rects, celebration paths and the scrubber pan are computed in LTR coordinates, and a mirrored Klondike layout is not what players expect (Microsoft Solitaire keeps the layout). Android: `I18nManager.isRTL` is read at process start — a switch to/from an RTL language may need an app restart for the chrome to flip (verify; document; acceptable).
- **Digits.** Game screen numbers stay Latin (cards are Latin). `{{count}}` interpolation is plain `String(n)`; `Intl` calls get `-u-nu-latn` appended to the locale tag so Arabic locales don't switch to Arabic-Indic digits in the score while the move counter is Latin.
- **Fonts.** UI text uses the system font (`AppText`, no `fontFamily`) → CJK, Cyrillic, Arabic, Hebrew fall back natively. The embedded `CardTextAndroid` family is only used for rank/suit glyphs (`CardVisual.tsx`) and never receives translated text — keep it that way (inline comment).
- **Screen readers.** All a11y labels are translated; card names are composed from `rank` + `suit` + a per-locale pattern (`"{{rank}} of {{suit}}"`, de `"{{suit}} {{rank}}"`), translators may reorder.
- **Vegas `$`.** Stays a literal `$` in every language (notional casino dollars, existing product decision in `scoring.ts`).

## Simplification ideas

- No `react-i18next`, no `<Trans>`, no namespaces, no lazy loading, no language persistence, no in-app picker.
- No app.json `locales` (name is "Soli" everywhere).
- No translation CLI; one snapshot file for stale detection.
- Delete the unrendered `description` fields of `animationPreferenceDescriptors` and `statisticsPreferenceDescriptors` in `src/state/settings.tsx` (comment there says they are unrendered) instead of translating dead copy. Trade-off: if descriptions are wanted later they are re-added as keys.
- Dev-only UI stays English and outside `en.json`: Demo sheet (`app/(tabs)/index.tsx` DemoSheet labels), "Developer"/"Animations" settings sections and their rows, celebration mode names, `CelebrationDebugBadge`, `DemoPlaylistHud`, demo launcher descriptions, devLog messages. Mark each with a one-line `// i18n: dev-only, intentionally English` comment so a later sweep doesn't "fix" them.
- Card a11y names composed from 13 + 4 + 1 keys instead of 52.
- Share one `common.cancel` / `common.off` key, but do NOT reuse a key across different meanings (Mango learning: a key's namespace is the translator's context).

- **Allow-list is per language now** (review V2's suggestion): `UNTRANSLATED_OK` maps key → languages. Every entry was checked against the files: `hud.total` de / fr / es / pt-BR «Total»; `hud.score`, `history.score` fr / nl «Score»; `settings.scoring.standard` de / fr / it «Standard»; `hud.vegasSpoken` fr / nl («dollar», «dollars»); `time.minutes` fr; `a11y.rank.6` fr «Six»; `game.hint` nl «Hint»; `history.stats.incomplete` it «Incomplete» (feminine plural). The locale test therefore checks what the iOS device asks for. Unknown for Android if its Hermes uses the system ICU (issue 18).
- **Digits (issue 15): text replace, not a locale trick.** `toLatinDigits` maps U+0660–0669, U+06F0–06F9, U+066C → `,`, U+066B → `.`. Chosen over "drop the region for `ar`" because that loses the region's date conventions and is unverified on Android. Node prints Arabic-Indic digits for `ar-EG` too, so the jest test exercises the real case (with a guard assertion).
- **`time.join` is applied pairwise** (`parts.reduce`), so one two-placeholder pattern covers two and three parts, and `Intl.ListFormat` (not in Hermes) is not needed. A single space as a VALUE would fail the "no empty values" test (`trim()`), which is why the key is a pattern with placeholders.
- **Hebrew cannot use the same trick with one pattern:** «ו» takes a hyphen before a digit («ו-5 דקות») and none before a word («ודקה אחת»).
- No raw U+200E / U+200F in `ar.json` / `he.json` (grep count 0); the marks are JSON escapes.
- `yarn format:check` still fails on files that were unformatted at HEAD (e.g. `src/solitaire/scoring.ts`); only new i18n files and the files of this step were formatted. `src/i18n`, `src/utils`, `test/unit/i18n`, `test/unit/store` are clean.

From implementation, phases 0–3 (implementer A, 2026-11-23):

- **Android does NOT recreate the Activity on a language change**: the plugin's undocumented option `allowDynamicLocaleChangesAndroid` defaults to `true` and adds `locale|layoutDirection` to `android:configChanges` (plugin source + `expo config --type introspect`). The planning note "Activity is recreated" is therefore wrong; the AppState remount (1.6) is the only thing that updates the UI on Android.
- `Locale.languageScriptCode` exists in 58.0.5 → the zh rule uses it, no tag parsing.
- Never build an Intl tag by appending to `languageTag`: Android tags can already carry a `-u-…` extension and a second one is a RangeError. `getIntlLocale()` builds `<language>-<region>-u[-hc-h23|h12]-nu-latn` from parts. The `hc` part passes on the device's 12/24 h setting, which `Intl.DateTimeFormat(undefined)` used to honour and an explicit locale drops.
- `{{count}}` always triggers plural lookup in i18next. "Draw 3" (a mode name) therefore uses `{{number}}`.
- `i18next.t` is bound to the instance (`bindMemberFunctions`), so `export const t = i18next.t` is safe.
- A language is "supported" at runtime only when its JSON is REGISTERED in `src/i18n/index.ts` (the resolver gets that list). Unregistered languages fall through like unknown ones, so a half-delivered translation run never ships mixed text — but see issue 9.
- `describe.each([])` throws in jest → the per-locale block uses `forEach` so the suite passes with `en` only.
